Was zum Nachbauen nötig ist

Beide Proxmox-Produkte schreiben von sich aus nach InfluxDB 2 – aber sie schreiben nicht dasselbe, und der Proxmox Backup Server schreibt deutlich weniger, als ein Backup-Dashboard braucht. Das ist der wichtigste Punkt auf dieser Seite.

1 · Metrik-Server einrichten

In beiden Oberflächen unter Datacenter → Metric Server bzw. Configuration → Metric Server einen Server vom Typ InfluxDB anlegen:

FeldWertAnmerkung
ProtocolHTTPnicht UDP – UDP kann kein Influx 2
Server / Port192.168.x.x / 8086dieselbe Influx wie beim HA-Dashboard
Organizationmeine-org
Bucketproxmoxeigener Bucket, nicht der HA-Bucket
TokenAPI-Token mit SchreibrechtGrafana braucht separat ein Leserecht
Interval10 sStandard, reicht völlig

Ein eigener Bucket ist die bessere Wahl: Proxmox schreibt mit anderen Tag-Sätzen als die Home-Assistant-Integration, und eine getrennte Retention (z. B. 90 Tage statt unbegrenzt) hält die Datenbank klein.

2 · Datenmodell prüfen, bevor du Panels baust

Die Feldnamen unterscheiden sich zwischen PVE-Versionen. Führe diese Query einmal im Influx-Data-Explorer oder in einem Grafana-Panel aus und richte die Dashboards nach dem aus, was tatsächlich ankommt:

import "influxdata/influxdb/schema"

schema.measurements(bucket: "proxmox")

// und je Measurement:
schema.fieldKeys(bucket: "proxmox", predicate: (r) => r._measurement == "cpustat")
schema.tagKeys(bucket: "proxmox",   predicate: (r) => r._measurement == "system")

Die entscheidende Lücke: PBS schickt über den Metric Server nur Host- und Datastore-Metriken. Kein Task-Ergebnis, keine Snapshot-Zahlen, keine Backup-Dauer, kein Dedup-Faktor, kein Verify- oder GC-Status. Alle Panels im Mockup, die mit PBS-API gekennzeichnet sind, brauchen eine zweite Datenquelle.

3 · PBS-API als zweite Datenquelle

Für die Backup-Panels das Plugin Infinity (kostenlos, in Grafana OSS installierbar) als JSON-Datenquelle einrichten. In PBS unter Access Control → API Token ein Token für einen Benutzer mit der Rolle Audit anlegen – lesend genügt.

URL     https://pbs.fritz.box:8007
Header  Authorization: PBSAPIToken=grafana@pbs!readonly:<secret>

# Endpunkte, die die Panels im Mockup füllen:
GET /api2/json/admin/datastore/{store}/status      → Belegung, Dedup, Zähler
GET /api2/json/admin/datastore/{store}/snapshots   → Snapshot-Liste je Gast
GET /api2/json/admin/datastore/{store}/gc          → letzter Garbage-Collect
GET /api2/json/nodes/localhost/tasks?limit=200     → Task-Historie (Status, Dauer)

Läuft PBS mit selbstsigniertem Zertifikat, in der Infinity-Datenquelle Skip TLS Verify setzen – oder besser das PBS-Zertifikat in den Grafana-Container mounten.

4 · Bewusst getroffene Entscheidungen

  • Reichweiten-Panels statt reiner Belegungsanzeigen. „Storage zu 78 % voll" ist erst dann eine Information, wenn danebensteht, dass das in 40 Tagen 100 % sind. Die Prognose ist eine simple lineare Fortschreibung über 14 Tage – das genügt für Homelab-Wachstum und braucht kein ML-Plugin.
  • Schwellenfarben nur mit Zahl. Grün/Gelb/Rot steht nie allein, überall daneben der Wert oder ein Statuswort – sonst ist das Dashboard für rot-grün-blinde Betrachter unlesbar.
  • Serienfarben ≠ Statusfarben. Blau/Gelb/Grün/Violett sind für Zeitreihen mit mehreren Serien reserviert, die Schwellenrampe für Zustände. Sonst heißt Rot mal „kritisch" und mal „Serie 5".
  • Ein Panel „Datenaktualität" pro Dashboard. Der häufigste Fehlerfall ist nicht die kaputte VM, sondern der Metric Server, der seit drei Tagen nichts mehr schreibt – und ein Dashboard, das dabei fröhlich den letzten Wert weiterzeigt.
  • Keine Dual-Axis-Panels. Zwei Y-Achsen in einem Diagramm erzeugen beliebige Scheinkorrelationen. Wo zwei Größen zusammengehören, aber unterschiedlich skalieren, stehen zwei Panels nebeneinander.
